# Многопользовательская Iva с изолированной памятью

Дата: 2026-08-07
Статус: утверждено пользователем

## 1. Цель

Один self-hosted экземпляр Iva должен обслуживать до десяти взаимно недоверенных
людей через одного Telegram-бота. Каждый человек получает независимого личного
ассистента: его диалоги, память, файлы, настройки, расписания и интеграции не
смешиваются с данными других пользователей.

Владелец сервера оплачивает общие AI- и speech-to-text-провайдеры. Он может
технически открыть пользовательские файлы на сервере, но Iva не предоставляет ему
Telegram-команду или иной прикладной интерфейс для чтения чужой памяти.

## 2. Область первой версии

Первая версия поддерживает:

- до десяти активных пользователей;
- только личные чаты с ботом;
- ручное добавление, блокировку и удаление пользователей владельцем через локальную
  CLI;
- отдельные vault, runtime-состояние, сессии, настройки, расписания, вложения,
  интеграции и учёт использования;
- общие сервер, код, Telegram-бот и оплачиваемые владельцем провайдеры;
- конфигурируемые индивидуальные лимиты;
- безопасную миграцию существующего single-user vault владельца.

В первую версию не входят:

- групповые чаты и Telegram topics;
- общая семейная или командная память;
- самостоятельная регистрация и ссылки-приглашения;
- пользовательский экспорт vault;
- Telegram-доступ администратора к чужим данным;
- Telegram userbot для обычных пользователей.

## 3. Архитектура

Система состоит из трёх границ.

### 3.1. Telegram-шлюз

Единственный poller получает Telegram updates и остаётся единственным владельцем
ingress-очереди. До постановки сообщения в очередь он:

1. проверяет, что сообщение пришло из личного чата;
2. извлекает Telegram `from.id` из проверенного update;
3. находит активную запись пользователя в контрольном реестре;
4. проверяет ingress-лимиты;
5. направляет update только в процесс, закреплённый за этим пользователем.

Текст сообщения, callback data, `chat_id`, username и любые переданные моделью
значения не могут выбирать tenant. Единственным ключом маршрутизации служит
проверенный числовой Telegram user ID.

Неизвестные и заблокированные ID не создают каталоги и процессы. Групповые updates
не попадают ни в один пользовательский контекст.

### 3.2. Контрольная плоскость

Локальный реестр хранит только данные управления:

- Telegram user ID;
- статус `active` или `blocked`;
- роль `owner` или `user`;
- назначенный runtime endpoint;
- лимиты и счётчики;
- версию пользовательского layout.

Реестр расположен вне пользовательских vault, записывается атомарно, имеет права
`0600` и недоступен инструментам обычного пользователя. Изменять его может только
локальная CLI владельца.

Минимальные команды:

```text
iva users list
iva users add <telegram-id>
iva users block <telegram-id>
iva users unblock <telegram-id>
iva users limits <telegram-id> ...
iva users delete <telegram-id> --confirm <telegram-id>
```

`list` показывает идентификатор, статус, состояние процесса и расход, но не выводит
содержимое памяти, имена файлов или интеграционные секреты.

### 3.3. Персональные процессы Iva

Для каждого активного пользователя диспетчер запускает отдельный процесс Iva с
персональными путями и runtime-настройками. Процесс не меняет tenant во время жизни.
Это позволяет сохранить существующую single-user модель компонентов вместо
динамической подмены глобального `process.env` между параллельными запросами.

Каждому процессу назначаются собственные:

- `ASSISTANT_VAULT_DIR`;
- `ASSISTANT_DATA_DIR`;
- Eve session и workflow storage;
- run-status, queue и update ledger;
- настройки языка, часового пояса, модели и персоны;
- memory rollups, digest, reminders и schedules;
- Google Workspace credentials;
- usage journal и quota state.

Общий Telegram poller маршрутизирует сообщения, а диспетчер контролирует запуск,
остановку и health каждого процесса. Сбой одного процесса не останавливает соседние.

## 4. Layout данных

Базовый каталог задаётся `ASSISTANT_USERS_DIR`; безопасный default находится внутри
уже игнорируемого runtime-каталога `data/users`.

```text
data/
├── control/
│   ├── users.json
│   ├── users.lock
│   └── gateway/
└── users/
    └── <telegram-id>/
        ├── vault/
        ├── runtime/
        ├── sessions/
        ├── integrations/
        └── usage/
```

Каталог пользователя создаётся с правами `0700`, файлы с секретами — `0600`.
Идентификатор проходит строгую проверку как положительное десятичное целое и затем
сверяется с реестром. Все вычисленные пути проходят `resolve`/realpath-проверку на
принадлежность персональному корню.

Пользовательские данные остаются untracked. `.gitignore` продолжает закрывать `.env`,
`.env.*`, `data`, `attachments` и `/vault/`; обновление не имеет права сужать эти
правила.

## 5. Граница инструментов

Текущие `bash`, `read_file` и связанные host-native инструменты имеют доступ ко всей
файловой системе сервера. Само разделение процессов не делает их безопасными для
взаимно недоверенных пользователей.

Поэтому все Telegram workers, включая `owner`, получают персонально ограниченный
tool profile:

- модель не получает host-native `bash`, системные команды, управление сервисом или
  произвольные абсолютные пути;
- файловые инструменты принимают только пути внутри vault/runtime root текущего
  пользователя;
- `glob`, `grep`, memory search, чтение, запись и вложения используют единый
  bounds-checking resolver;
- resolver запрещает абсолютные пути, `..`, NUL, выход через symlink и замену
  проверенного родителя между проверкой и записью;
- команды меню и синтетические updates повторно проходят проверку user ID и роли.

Полный доступ к host shell остаётся только у владельца в локальном терминале сервера,
вне Telegram и model tool-calling. Owner role внутри Iva разрешает owner-only
интеграции, но не снимает файловые границы. Секреты общих провайдеров не передаются
model-driven инструментам. Outbound secret gate остаётся дополнительным слоем, но не
считается основной границей изоляции.

## 6. Интеграции и секреты

AI-, vision- и speech-to-text-ключи принадлежат серверной инфраструктуре и
оплачиваются владельцем. Usage каждого вызова маркируется tenant ID до отправки
провайдеру и атомарно учитывается в персональном журнале.

Google Workspace подключается отдельно в каждом личном чате. OAuth state привязан к
user ID, а credentials записываются только в `integrations` этого пользователя.
Callback для другого пользователя или повторное использование завершённого state
отклоняются.

Telegram userbot сохраняется только в owner profile. Обычный пользователь не видит
его меню, MCP-инструменты, session string и статус подключения.

## 7. Лимиты

Новые пользователи получают следующие defaults:

| Ресурс                      |    Лимит |
| --------------------------- | -------: |
| Одновременные model turns   |        1 |
| Запросы в час               |       30 |
| Запросы в сутки             |      100 |
| LLM tokens в сутки          |  500 000 |
| Распознавание аудио в сутки | 30 минут |
| Одно вложение               |    20 МБ |
| Все персональные данные     |     1 ГБ |

Лимиты настраиваются индивидуально через CLI. Окна считаются по серверному UTC и
хранят начало периода, использованное количество и версию политики. Проверка
выполняется до постановки дорогой работы в очередь; итоговое фактическое использование
добавляется после завершения вызова.

Если лимит исчерпан, бот сообщает тип лимита и время сброса. Данные не удаляются,
активные процессы других пользователей не затрагиваются. Один запрос может превысить
оставшийся token budget только в пределах заранее установленного максимума одного
turn; следующий запрос будет отклонён.

## 8. Жизненный цикл пользователя

### Добавление

`iva users add` валидирует ID, создаёт приватный layout из vault template, записывает
реестр атомарно, запускает процесс и проверяет health. Если любой шаг не удался,
пользователь не становится active, а частично созданный layout сохраняется для
диагностики без повторного использования чужим ID.

### Блокировка

`block` сначала переводит запись в `blocked`, после чего шлюз перестаёт принимать
новые updates. Затем диспетчер завершает активный turn в ограниченное время,
останавливает процесс и schedules. Данные сохраняются.

### Удаление

Удаление доступно только локально и требует повторить точный Telegram ID в
`--confirm`. Сначала пользователь блокируется, затем его каталог перемещается в
закрытый quarantine с меткой времени. Немедленного необратимого `rm -rf` нет.
Политика окончательной очистки quarantine находится вне первой версии.

## 9. Миграция существующей установки

Миграция должна работать под старой установленной CLI: новый код, полученный после
update, нельзя считать уже запущенным до следующего restart/build этапа.

Порядок миграции:

1. Проверить, что legacy-конфигурация содержит ровно один разрешённый Telegram ID.
2. Если ID несколько или нет ни одного, остановиться до любых изменений и потребовать
   явно указать owner.
3. Остановить ingress после сохранения durable queue.
4. Создать приватный owner layout и резервную копию legacy vault/data/session paths.
5. Скопировать данные, сравнить количество файлов, размеры и SHA-256 обычных файлов.
6. Атомарно записать owner в реестр и переключить пути.
7. Выполнить build, запустить gateway и owner worker.
8. Проверить health, Telegram round-trip, memory search, attachment lookup, settings и
   schedules.
9. Сохранить legacy backup и manifest отката; не удалять их автоматически.

Повторный запуск миграции идемпотентен. При ошибке до переключения продолжает работать
legacy layout; при ошибке после переключения выполняется откат по manifest.

## 10. Ошибки и восстановление

- Недоступный worker получает bounded restart с backoff; сообщения остаются в
  персональной durable queue.
- Ошибка одного tenant не блокирует polling и очереди остальных.
- Повреждённый registry, quota state или routing record приводит к fail-closed
  поведению; файл помещается в quarantine, пользователь не перенаправляется в default
  tenant.
- Неизвестный runtime endpoint никогда не заменяется owner endpoint.
- При недостатке диска новые вложения и записи отклоняются до частичной записи.
- Диспетчер восстанавливает процессы только из валидного контрольного реестра.
- Логи содержат tenant ID, тип операции и error ID, но не содержимое сообщений,
  credentials или абсолютные пользовательские пути.

## 11. Совместимость обновлений

`iva update`, setup, doctor, start, stop, restart и systemd generation получают
явную поддержку gateway и набора workers. Любое изменение `agent/` требует
`npm run build` до запуска процессов.

Single-user установки мигрируются один раз. Новые persisted-форматы имеют версию и
читатель предыдущей версии. Обновление не предполагает, что новый update-flow уже
исполняется под только что загруженным кодом.

## 12. Проверка и критерии готовности

Функция готова, когда свежие доказательства подтверждают:

1. Два активных ID одновременно общаются с одним ботом и попадают в разные workers.
2. Их Eve sessions, queue, run-status, memory, settings, attachments, schedules,
   integrations и usage физически разделены.
3. Пользователь A не может прочитать или изменить данные B через обычные сообщения,
   callbacks, menu flows, абсолютные пути, traversal, symlink, quoted context,
   повтор Telegram update или synthetic update.
4. Ни один Telegram-пользователь, включая owner, не может вызвать host-native bash,
   systemctl, update или произвольное чтение сервера; userbot доступен только owner и
   не снимает файловых границ.
5. Владелец через Telegram не получает прикладной команды чтения чужих данных.
6. Лимиты считаются независимо и не влияют на соседнего пользователя.
7. Блокировка прекращает ingress и schedules только выбранного пользователя.
8. Перезапуск восстанавливает персональные очереди без перекрёстной доставки.
9. Google credentials и OAuth state нельзя применить к другому ID.
10. Legacy owner сохраняет память, вложения, настройки и расписания после проверенной
    миграции и может откатиться по manifest.
11. Тесты, typecheck, lint и обязательный build проходят на поддерживаемом Node 24 и
    Linux runtime.
12. README и эксплуатационная документация больше не обещают single-user-only режим
    и точно описывают границы: владелец сервера технически контролирует хост.

## 13. Порядок реализации

Реализация будет разбита на вертикальные этапы:

1. Версионированный user registry, CLI и персональный layout.
2. Tenant-aware Telegram routing и отдельные durable queues.
3. Worker lifecycle и персональные Eve runtime paths.
4. Ограниченный tool profile и единый safe path resolver.
5. Quota accounting и отказ до дорогих операций.
6. Персональные schedules и Google Workspace credentials; owner-only userbot.
7. Legacy migration, rollback и update compatibility.
8. End-to-end isolation tests, build, документация и эксплуатационная проверка.

Каждый этап должен оставлять существующего владельца работоспособным и не открывать
частично изолированный режим обычным пользователям до прохождения security regression
tests.
